Module 1: Network connectivity types

A VPC reaches the physical network through a transit gateway (TGW). VCF 9 gives you two ways to build it, and the lab sets up both on the same site.

Distributed TGWCentralized TGW
Where routing happensOn every ESX hostOn NSX Edge nodes
Edge nodes neededNoYes, an edge cluster
Physical network needsThe external VLAN on every hostBGP (or static) routing to the ToR switches
Good forSimple, fast setupStateful services such as NAT on the edges

Distributed transit gateway

I configured the site's transit gateway as distributed: external traffic leaves on a VLAN straight from the hosts, so there are no edges in the path.

IP block values:

  • VPC_Ext_Block: 10.1.21.0/25
  • Priv_VPC_TGW_Block: 10.1.19.128/26

To try the centralized option on the same site, the distributed setup has to go first. The lab provides a pre-written script that removes it from the CLI in three steps: disconnect the TGW attachments, clear the IP blocks from the VPC connectivity profile, and delete the distributed VLAN connection.

Centralized transit gateway

A centralized TGW sends north-south traffic through NSX Edge nodes, so it has a longer list of prerequisites.

The ones that matter most: plan an Edge TEP VLAN (the host TEP VLAN can be reused), make sure the cluster can fit at least two edge nodes (they reserve 100% of their memory), have two BGP peers ready on the ToR switches, and use external IP blocks that don't overlap with management, uplink or Edge TEP subnets.

Edge configuration. A centralized gateway needs an edge cluster to host it, so I configured a two-node edge cluster.

Uplinks for edge-mgmt-01a, with the BGP configuration:

BGP checklistBoth peering routers need connectivity to each other. If there's a firewall in between, TCP 179 must be open. And the BGP values (ASN, neighbor IP, password) must match on both sides.

Edge uplink 2 is optional, but recommended for redundancy. Then the uplink for edge-mgmt-02a; the BGP ASN and password are pre-populated.

IP blocks:

  • VPC external IP block: 10.11.0.0/24
  • Private - TGW IP block: 192.168.4.0/24

Test connectivity

From the main console: web-01a and app-01a answer, but db-01a doesn't. The Private - VPC subnet can't be reached from anything outside its VPC.

ping -c 2 web-01a.site-a.vcf.lab
ping -c 2 app-01a.site-a.vcf.lab
ping -c 2 192.168.2.3

From web-01a (over SSH):

  • ping -c 2 172.31.0.179: app-01a's internal IP is reachable. Its transit subnet allows traffic between VPCs in the same private cloud. The main console can't reach this IP; it used app-01a's external NAT address instead.
  • ping -c 2 192.168.2.3: db-01a is not reachable. It sits on a Private - VPC subnet in a different VPC.

From app-01a (over SSH), all three succeed:

  • web-01a: the Private - TGW subnet reaches web-01a in the other VPC.
  • db-01a: both subnets are in the same VPC.
  • 10.1.10.130: the main console, outside the VPC, through app-01a's external NAT address.

Key takeaways

  • A distributed TGW is the quickest path: no edges, but the external VLAN has to be on every host.
  • A centralized TGW needs an edge cluster and BGP to the ToR switches, so plan the prerequisites first.
  • The subnet type decides reachability: Public, Private - TGW or Private - VPC.
  • Projects, quotas and roles let the network team hand day-to-day work to tenants without losing control.
