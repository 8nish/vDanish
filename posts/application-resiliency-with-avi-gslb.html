What GSLB needs

GSLB runs on DNS. A DNS virtual service answers the queries for the global apps with the VIP of whichever site is best at that moment. So before anything else, each region needs one.

Module 3: A basic global service

A GSLB service is one global app with one FQDN, backed by virtual services in the sites. First a check that the DNS virtual service is up:

Applications > GSLB Services > Create:

Two GSLB pools, one per site. The higher priority wins, so Palo Alto at 20 takes all the traffic while its health monitor passes, and Barcelona at 10 only takes over if Palo Alto goes down. That's active/standby, like a DR site.

Module 4: An advanced global service

A GSLB pool isn't a server pool. It groups virtual services across sites, and a member can also be a plain IP, like a standalone server or another vendor's load balancer.

EDNS Client Subnet lets a DNS resolver pass the client's subnet along with the query. Without it, Avi only sees the resolver's IP.

Palo Alto mixes two virtual services and one plain IP, the standalone web server in region A. It uses consistent hash, so the same client IP, or the same EDNS subnet, always lands on the same member. A bit like persistence:

Barcelona gets priority 5, so it's the backup, with two plain IPs:

A 2 second TTL makes clients ask again almost right away, so a failover shows up fast. If every member is down, it still answers with all the records instead of nothing.

One of my misconfigsadv-app's domain came out as system-gslb-http.global.vcf.lab. It should be adv-app.global.vcf.lab.

Module 5: A geo-aware global service

Here the DNS answers with the site closest to the client. For that it needs a geo DB, a file that maps IP ranges to locations. Every DNS Service Engine loads its own copy.

Geo DB

Infrastructure > GSLB > Geo Profile > Create:

secure-app

One pool with a virtual service from each site. The lab has both members inherit their location from their site, so the Palo Alto and Barcelona coordinates from Module 2 get used:

Testing it with dig

dig with +subnet pretends to be a client somewhere else. 139.47.28.29 is a Barcelona address, so the answer should be a 10.1.14.x VIP:

It can come back as either site. The resolver on the console strips the EDNS option, so Avi only sees the resolver's internal IP. That IP isn't in the geo DB, so it falls back to round robin. Sending the query straight to the DNS virtual service with dig @10.1.13.137 keeps the subnet, and then the closest site comes back.

Key takeaways

  • GSLB is DNS. The DNS virtual service answers with one site's VIP, then the client goes straight to that site.
  • Each region gets its own DNS virtual service, listening on UDP and TCP 53.
  • All GSLB config is done on the leader. Followers are read-only and stay in sync.
  • GSLB pool priority gives active/standby. The higher number wins.
  • Geo load balancing needs the real client IP. If the resolver strips EDNS, it falls back to round robin.
