This lab builds a two-site NSX Federation setup: Palo Alto and Frankfurt, about 10 ms apart. I onboarded Frankfurt into the Global Manager, gave its edge a remote tunnel endpoint, stretched the Tier-0 across both sites with BGP to each site's routers, and put a two-tier app on stretched segments. Module 5, the failover test, didn't work for me; more on that at the end. Click any photo to see it full screen.

Lab topology

Palo Alto is the primary location and already sat under the Global Manager. Frankfurt starts as a standalone NSX Manager. By the end, one Tier-0 and one Tier-1 span both sites, and the web and DB segments exist in both.

Module 1: NSX Federation fundamentals

Module 1 is reading only, but it is the part the rest of the lab depends on:

  • The Global Manager (GM) holds config that applies to several locations. There is an active GM and a standby in the other site.
  • Each site keeps its own Local Manager (LM). Objects pushed from the GM show up there as global objects, and the GM version wins over local config.
  • RTEPs (remote tunnel endpoints) on the edges carry overlay traffic between sites. They are separate from the normal TEPs used inside a site.
  • A stretched Tier-0 has a primary and secondary location. North-south traffic leaves through the primary while it is up.

Module 3: Tier-0 BGP at the provider boundary

The Tier-0 already runs in Palo Alto. This module stretches it to Frankfurt and peers it with Frankfurt's routers.

Uplink VLAN segments

From the GM, created an uplink segment for VLAN 49 in Frankfurt:

And one for VLAN 50, also in Frankfurt:

They are made on the GM so the stretched Tier-0 can use them, but scoped to nsx-mgmt-b because those VLANs only exist in Frankfurt. Two uplinks to two different routers means losing one router doesn't cut the site off.

Stretch the Tier-0 to Frankfurt

Networking > Tier-0 Gateways, then Edit on the existing gateway:

Added nsx-mgmt-b as a location in Secondary mode with edge cluster edgecl-mgmt-b, and left Mark all locations as Primary off:

Primary and secondary decides where traffic leaves. While Palo Alto is healthy, all north-south traffic goes out there, and Frankfurt only takes over if Palo Alto fails. Making both primary would send traffic out of both sites, which is fine, but then you have to keep return traffic symmetric yourself.

Uplink interfaces in Frankfurt

Added two external interfaces on the stretched Tier-0, one per uplink VLAN, both on edge-mgmt-01b:

All four interfaces showed Success. int-19 and int-20 are the existing Palo Alto ones:

BGP neighbors

Then the two Frankfurt neighbors. The details have to match what the routers expect, or the sessions won't come up:

  • Source address is the interface on the same VLAN as the router (10.2.6.2 for 10.2.6.1, 10.2.6.130 for 10.2.6.129). The router only accepts the session from the address it has configured.
  • Max hop limit 1 because each router is directly connected.
  • Neighbor local AS 65006. The Tier-0 runs as AS 65001, but Frankfurt's routers are set up to peer with 65006. Overriding the local AS for just these two neighbors avoids changing the routers, and Palo Alto still sees 65001.

All four sessions came up. Palo Alto peers with AS 65000, Frankfurt with AS 65005:

Route redistribution for Frankfurt

Redistribution is set per location. Palo Alto already had a rule; Frankfurt had none, so it wasn't advertising anything yet. On the same Tier-0, under Route Re-distribution, Set next to nsx-mgmt-b:

Inter-SR iBGP in that photo is what lets the Tier-0's service routers in both sites share routes with each other over the RTEP.

Prefix list

Routing > IP Prefix Lists on the Tier-0, then a new list with two entries, both permit: 10.1.13.128/25 and 10.1.13.0/25. Those are the web and DB subnets coming in Module 4.

Route map with an AS path prepend

Then Route Maps, and a new one called Route-Map-Site-B:

One match criterion: type IP Prefix, members set to the prefix list from before, AS path prepend 65006, action Permit:

Apply it to the Frankfurt neighbors

Back in BGP, BGP Neighbors > Set:

Edited the route filter on 10.2.6.1 and set the IPv4 Out Filter to Route-Map-Site-B:

And the same for 10.2.6.129:

Why prepend only in FrankfurtBoth sites advertise the same workload subnets. With the prepend, the path through Frankfurt looks one AS longer, so the outside network sends return traffic to Palo Alto, the same site the traffic leaves from. Without it, replies could come back through Frankfurt, and any stateful firewall in the path would drop them because it never saw the outgoing packet. If Palo Alto goes down, its routes disappear and the longer Frankfurt path is the only one left. That switch is what Module 5 is meant to show.

Module 4: Tenant infrastructure

This needs the stretched Tier-0 and working BGP from Module 3. The goal is the bottom half of the diagram at the top: a stretched Tier-1 and two stretched segments for a web tier and a DB tier.

Stretched Tier-1

Networking > Tier-1 Gateways > Add Tier-1 Gateway on the GM. mgmt-t1-stretched, Distributed Only, linked to mgmt-t0-stretched, advertising all connected segments:

Distributed Only means the Tier-1 has no service router and needs no edge. It routes in the hypervisor kernel on every host, in both sites. Nothing here needs NAT or a gateway firewall, so there was no reason to give it one.

Stretched segments

A global segment for the web workloads, on the Tier-1, gateway 10.1.13.129/25:

And one for the DB workloads, gateway 10.1.13.1/25:

Because they're created on the GM, both segments exist in both locations with the same subnet and gateway. A VM can run in either site, or move between them, and keep its IP.

Check what Frankfurt advertises

On the stretched Tier-0's BGP neighbors, the menu on 10.2.6.1 has Download Advertised Routes. The CSV shows both workload subnets going to 10.2.6.1 from 10.2.6.2, with AS path 65006:

That confirms three things: the Tier-1 segments got redistributed, the prefix list matches them, and Frankfurt's routers see the routes from AS 65006.

With everything working, web to DB traffic is routed by the Tier-1 on the host and never leaves Palo Alto. Traffic to the outside, like the lab console on 10.1.10.130, goes Tier-1 to Tier-0 and out through edge-mgmt-01a to the Palo Alto routers. Frankfurt carries nothing until Palo Alto fails.

Key takeaways

  • Copy the new site's API cert thumbprint before onboarding it, and check version compatibility before saving.
  • RTEPs need their own routed VLAN and a WAN that carries the 1700-byte inter-location MTU.
  • A stretched Tier-0 in primary/secondary mode sends north-south traffic out of the primary site only. An AS path prepend on the secondary site keeps return traffic coming in the same way.
  • Neighbor local AS lets one Tier-0 present a different AS to different peers.
  • Global segments on a Distributed Only Tier-1 give both sites the same subnets and gateways with no edge in the path.
