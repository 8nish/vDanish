Module 2: Securing a 3-tier app with the DFW

The app is 3 web VMs, 2 app VMs running Tomcat and 1 MySQL database. Clients hit web on 443, web talks to app on 8080, app talks to db on 3306. There's no real front end. VMFlowGen makes the traffic and I watch it in Security Intelligence. VCF Operations for Logs is in the lab too.

Then Inventory > Groups, a group for the whole app:

If you do this labType the tag exactly: 3-tier-app, scope application. The group matches on it, and the rules depend on the group.

Module 3: Layer 7 rule for MySQL

App to Db allows the MySQL service, which is just TCP 3306. Anything on 3306 gets through, MySQL or not. A Layer 7 context profile looks at the payload instead, so only real MySQL matches.

To test it, change one of the app to db flows in VMFlowGen. app02a to db01a first:

app01a to db01a stays as it is:

While that applies, back to Security Explorer from Module 2. The red is gone:

Then in NSX, add the preconfigured MYSQL context profile to App to Db and publish:

app02a now sends Oracle on 3306, which doesn't match the profile, so it should turn Blocked. app01a didn't change, so it stays Allowed. This one takes a while to show:

Key takeaways

  • Unprotected in Security Intelligence means the flow only hit the default rule. Nothing written for it.
  • Tag, then group, then rule. One tag on six VMs covered the whole app.
  • Applied To keeps a rule on the VMs it's for instead of every VM in the DFW.
  • A Layer 7 context profile checks what's actually in the traffic, so the right port alone isn't enough.
  • GeoIP on the gateway firewall drops whole countries at the Tier-0.
